1. dbt practices at your scale (313 models, 58 jobs)

Incremental strategies

Strategy Use it for Example for you
merge + unique_key Upserts / CDC Bronze CDC from Supabase. Add a matched_condition so only newer LSNs update rows. Use liquid_clustered_by on the key
replace_where Recomputing a time window atomically, no key needed UA report and aggregates: rewrite the last N days
microbatch (dbt 1.9+) Large time-series, backfills in batches Amplitude events (multi-TB), daily batches
append Truly immutable logs only Rarely; risk of duplicates
Streaming table / MV materializations Ingestion and simple incremental aggregates run by Lakeflow pipelines Bronze-from-files/Kafka models as they move to dbt

"The Databricks adapter implements the microbatch strategy using replace_where." (dbt Databricks configs)

"For incremental microbatch models, if your upstream models don't have event_time configured, dbt cannot automatically filter them during batch processing and will perform full table scans on every batch run." (dbt microbatch)

"replace_where inserts data into columns in the order provided, rather than by column name." (dbt Databricks configs)

Biggest saving: check whether the 3× daily full refresh is still needed. If late-arriving data and restatements fall within a known window, a replace_where or microbatch lookback (for example, the last 7 days) on every run gives the same correctness at a fraction of the cost. You'd keep full refreshes for schema changes and occasional reconciliation. This is likely part of the +33% on SQL warehouses since the UA chain moved to dbt.

Keeping dbt test cheap

  • Test recent data only on big tables. Use the test where config, for example only the last 3 days of Amplitude, and run full-table tests on a daily or weekly tag.

  • Use thresholds instead of failing on any bad row:

    "You can use the error_if and warn_if configs to set custom failure thresholds in your tests." (dbt data tests)

  • Store failures only where someone acts on them. store_failures writes a table for each test run.

  • Run unit tests in CI only:

    "dbt Labs strongly recommends only running unit tests in development or CI environments. Since the inputs of the unit tests are static, there's no need to use additional compute cycles running them in production." (dbt unit tests)

  • CI builds only what changed: state:modified+ against the prod manifest, with --defer, on the CI warehouse (dbt state selection).

  • Push simple rules into Delta constraints. NOT NULL and CHECK constraints are enforced by Delta at write time, so they cost nothing at test time:

    "When a constraint is violated, the transaction fails with an error." (Constraints)

Adapter pinning

"Databricks recommends pinning your dbt tasks to a specific version of the dbt-databricks package to ensure the same version is used for development and production runs." (dbt task for jobs)

  • Pin exact versions (dbt-databricks==1.12.x, plus a matching dbt-core) in the serverless job environment.

    "DBT tasks use a job-level environment for library configuration." (Serverless dependencies)

  • Use the same pins everywhere: one constraints file shared by the bundle environment, GitHub Actions CI and local development.

  • Guard the project with require-dbt-version in dbt_project.yml (dbt docs).

  • Upgrade cadence:

    "Upgrade to new patch versions as soon as they're available. Upgrade to new minor versions when you're ready because you can only get some features and fixes on the latest minor version." (dbt Core versions)

    Do minor upgrades through a release PR, with a dev bundle run first.
