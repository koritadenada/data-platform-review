SQL warehouse topology, billing and dbt practices

Prepared by Databricks. Quotes are from the Azure Databricks documentation (learn.microsoft.com). dbt-specific behavior is quoted from the official dbt documentation (docs.getdbt.com) where the Azure docs don't cover it. Prices are Azure West Europe, Premium, list price.

This is a companion to the platform review and goes deeper on the SQL warehouse and dbt points.

1. SQL warehouse topology and billing

Shared autoscaling or per-workload isolation?

Recommendation: use a hybrid. Isolate by service level and query shape, and let workloads with similar behavior share an autoscaling warehouse. Sharing pools capacity and replaces many idle tails with one, which is where most of the savings come from. Isolate only where a heavy workload could make a time-critical one queue, or where you need billed cost per workload.

"Start with a single larger warehouse and let serverless features manage concurrency and performance. It is usually more efficient to size down if necessary than to start small and scale up." (Warehouse behavior)

Class Workloads Why separate Starting config
ETL hourly dbt + 3× daily full refresh Heavy, bursty; must not block BI Small, max 3–4 clusters, auto-stop 1 min (API)
BI Tableau live connections, analysts Interactive latency X-Small/Small, max 2–4, auto-stop 5–10 min
Automation (P0) P0 bots, LLM agents 15-minute SLA; never queue behind ETL 2X-Small, max 2, auto-stop 1 min
CI PR checks, dbt CI builds Spiky, cost belongs to engineering X-Small, max 2, auto-stop 1 min
Dev dbt dev, ad-hoc Keeps prod spend clean 2X-Small, max 2, auto-stop 1–5 min

The payment-webhook INSERTs come off SQL warehouses entirely (see the Zerobus Ingest recommendation in section 1 of the platform review).

Cost attribution inside a shared warehouse: billing rows carry the warehouse ID, so a warehouse is your billed unit. To split a shared warehouse's cost by team or model, use query tags. dbt-databricks 1.11+ sets them automatically (you're on 1.12).

"Query tags are custom key-value pairs you apply to SQL workloads so you can group, filter, and track costs on Databricks SQL warehouses [...]" (Query tags)

"Tags appear in the system.query.history table and on the Query History page of the Azure Databricks UI." (same page)

Query tags give you an estimated split. They don't appear in system.billing.usage. Tableau can set them through Initial SQL.

How serverless is billed for many short queries

  • Granularity:

    "A DBU is a unit of processing capability, billed on a per-second usage." (Azure Databricks pricing)

    No minimum charge per query is documented. - What you pay for: the time the warehouse is running, times the DBU rate for its size, times the number of running clusters. You don't pay per query. Serverless SQL is $0.91/DBU in West Europe, including compute (Databricks SQL pricing). - Idle tail: you pay until auto-stop.

    "Idle SQL warehouses continue to accumulate DBU and cloud instance charges until they are stopped." (Create a SQL warehouse)

    "The minimum is 5 minutes when you use the UI. Note that you can create a serverless SQL warehouse using the SQL warehouses API, in which case you can set the Auto Stop value as low as 1 minute." (same page)

  • Worked example: a bot query every 15 minutes, with a 10-minute auto-stop, keeps the warehouse up about 70% of the time. With a 1-minute auto-stop it's about 10%. Serverless restarts in "typically between 2 and 6 seconds" (Warehouse types), so short auto-stops cost very little latency.

  • Measure, don't estimate: group system.billing.usage by usage_metadata.warehouse_id and hour to get the actual DBUs per warehouse. Then compare before and after consolidation.

Size up or scale out?

"If queries are spilling to disk, increase the cluster size. Check for spills in the query profile." (Warehouse behavior)

"For workloads with many concurrent queries, configure a sufficient maximum number of clusters to handle peak loads." (same page)

Signal Action Typical case for you
Peak Queued Queries consistently > 0 Raise max clusters Hourly and full-refresh dbt overlap; Tableau at the top of the hour
Bytes spilled to disk in query profile Size up Full-refresh models on the subscription OBT
Both Size up and raise max clusters Check one model at a time

Extra clusters run only during the burst, while a bigger size costs more for the whole time the warehouse runs. So for your bursts, scaling out is usually cheaper.

Statement timeouts

"When the timeout is set at more than one scope, the first non-null value in the following order applies:" Session, then Warehouse (Beta), then Workspace. (STATEMENT_TIMEOUT)

"The system default is 172800 seconds (2 days)." (same page)

  • Workspace: lower the 2-day default to a safety net, for example 2 hours.
  • Warehouse level (Beta, enable in Previews): set one per class. For example BI 10 min, Automation 5 min, CI 30 min, Dev 30 min, and ETL about 2× your longest full-refresh model.
  • Session level: for known exceptions, e.g. a dbt pre-hook SET STATEMENT_TIMEOUT = ... on a heavy backfill.
  • Job level: a task-level timeout on each dbt job caps the whole run, not just a single statement (Configure a task).

2. dbt practices at your scale (313 models, 58 jobs)

Incremental strategies

Strategy Use it for Example for you
merge + unique_key Upserts / CDC Bronze CDC from Supabase. Add a matched_condition so only newer LSNs update rows. Use liquid_clustered_by on the key
replace_where Recomputing a time window atomically, no key needed UA report and aggregates: rewrite the last N days
microbatch (dbt 1.9+) Large time-series, backfills in batches Amplitude events (multi-TB), daily batches
append Truly immutable logs only Rarely; risk of duplicates
Streaming table / MV materializations Ingestion and simple incremental aggregates run by Lakeflow pipelines Bronze-from-files/Kafka models as they move to dbt

"The Databricks adapter implements the microbatch strategy using replace_where." (dbt Databricks configs)

"For incremental microbatch models, if your upstream models don't have event_time configured, dbt cannot automatically filter them during batch processing and will perform full table scans on every batch run." (dbt microbatch)

"replace_where inserts data into columns in the order provided, rather than by column name." (dbt Databricks configs)

Biggest saving: check whether the 3× daily full refresh is still needed. If late-arriving data and restatements fall within a known window, a replace_where or microbatch lookback (for example, the last 7 days) on every run gives the same correctness at a fraction of the cost. You'd keep full refreshes for schema changes and occasional reconciliation. This is likely part of the +33% on SQL warehouses since the UA chain moved to dbt.

Keeping dbt test cheap

  • Test recent data only on big tables. Use the test where config, for example only the last 3 days of Amplitude, and run full-table tests on a daily or weekly tag.

  • Use thresholds instead of failing on any bad row:

    "You can use the error_if and warn_if configs to set custom failure thresholds in your tests." (dbt data tests)

  • Store failures only where someone acts on them. store_failures writes a table for each test run.

  • Run unit tests in CI only:

    "dbt Labs strongly recommends only running unit tests in development or CI environments. Since the inputs of the unit tests are static, there's no need to use additional compute cycles running them in production." (dbt unit tests)

  • CI builds only what changed: state:modified+ against the prod manifest, with --defer, on the CI warehouse (dbt state selection).

  • Push simple rules into Delta constraints. NOT NULL and CHECK constraints are enforced by Delta at write time, so they cost nothing at test time:

    "When a constraint is violated, the transaction fails with an error." (Constraints)

    dbt applies model-contract constraints on Databricks after the table is built, so we'll check this behavior with your setup in a sandbox before you replace tests with constraints.

Adapter pinning

"Databricks recommends pinning your dbt tasks to a specific version of the dbt-databricks package to ensure the same version is used for development and production runs." (dbt task for jobs)

  • Pin exact versions (dbt-databricks==1.12.x, plus a matching dbt-core) in the serverless job environment.

    "DBT tasks use a job-level environment for library configuration." (Serverless dependencies)

  • Use the same pins everywhere: one constraints file shared by the bundle environment, GitHub Actions CI and local development.

  • Guard the project with require-dbt-version in dbt_project.yml (dbt docs).

  • Upgrade cadence:

    "Upgrade to new patch versions as soon as they're available. Upgrade to new minor versions when you're ready because you can only get some features and fixes on the latest minor version." (dbt Core versions)

    Do minor upgrades through a release PR, with a dev bundle run first.
