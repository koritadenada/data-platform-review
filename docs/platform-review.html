Data platform review: answers to the open questions

Overall: the platform is in good shape (code-managed bundle, contracts in CI, Terraform-owned grants, UC throughout). Most of the points below are configuration and consolidation, not re-architecture.

1. SQL warehouses

1a. Consolidation and idle cost

Recommendation: you've already consolidated from 16 warehouses to 3 core ones (with a 12% monthly cost reduction, together with the instance pool changes). Keep that shape, one warehouse per workload class, and let serverless scaling absorb the overlaps. The one class worth keeping separate is the P0 automation (the bot feeds), so it never queues behind ETL. Sharing a warehouse pools capacity and replaces several idle tails with one, which is where most of the savings come from.

How serverless is billed: DBUs are billed per second. You pay for the time the warehouse runs (× its size × the number of running clusters), not per query. Serverless SQL is $0.91/DBU in West Europe, including compute (pricing).

"Idle SQL warehouses continue to accumulate DBU and cloud instance charges until they are stopped." (Create a SQL warehouse)

That idle tail is why auto-stop matters. A bot querying every 15 minutes keeps a warehouse with a 10-minute auto-stop up about 70% of the time, but only about 10% with a 1-minute auto-stop. Restarting takes "typically between 2 and 6 seconds" (Warehouse types).

What to change:

  • Set auto-stop to 1 minute through the API (Terraform) on the low-traffic warehouses.

    "The minimum is 5 minutes when you use the UI. Note that you can create a serverless SQL warehouse using the SQL warehouses API, in which case you can set the Auto Stop value as low as 1 minute." (Create a SQL warehouse)

  • Take the payment-webhook single-row INSERTs off SQL warehouses. n8n can post to Zerobus Ingest over REST, which writes straight into Delta and is billed as serverless ingest, so it doesn't keep a warehouse awake (details in 4a).

    "Zerobus Ingest is a push-based streaming API that writes data straight into Unity Catalog Delta tables at high scale, with no message bus to run." (Zerobus Ingest overview)

  • Find the bots in system.query.history (by client application or user). Then batch them onto a schedule or point them at the BI warehouse.

  • Measure before and after: group system.billing.usage by usage_metadata.warehouse_id and hour.

1b. Size up or scale out?

"If queries are spilling to disk, increase the cluster size. [...] For workloads with many concurrent queries, configure a sufficient maximum number of clusters to handle peak loads." (Warehouse behavior)

Signal Action Typical case for you
Peak Queued Queries consistently above 0 Raise max clusters Hourly and full-refresh dbt runs overlapping; Tableau at the top of the hour
Bytes spilled to disk in the query profile Size up Full-refresh models on the subscription OBT

Extra clusters run only during the burst, while a bigger size costs more for the whole time the warehouse runs, so scaling out is usually the cheaper fix for your bursts. The dbt warehouse is close to using all 3 of its clusters, so raise its maximum first.

1c. Cost attribution

To get under 5% unattributed spend: use serverless usage policies for notebooks, jobs and Genie, warehouse tags for SQL, and account budgets for alerts.

"Serverless usage policies consist of tags that are applied to any serverless compute activity incurred by a user assigned to the policy." (Public Preview, Usage policies)

"Budgets enable you to monitor usage across your account." (Budgets)

Inside a shared warehouse: billing rows carry the warehouse ID, so a warehouse is your billed unit. To split a shared warehouse's cost by team or model, use query tags. dbt-databricks 1.11+ sets them automatically (you're on 1.12).

"Query tags are custom key-value pairs you apply to SQL workloads so you can group, filter, and track costs on Databricks SQL warehouses [...]" (Query tags)

"Tags appear in the system.query.history table and on the Query History page of the Azure Databricks UI." (same page)

Query tags give you an estimated split. They don't appear in system.billing.usage; they land in the query_tags column of the query history system table.

How to set them per tool (overview, SET QUERY_TAGS syntax):

dbt: dbt-databricks 1.11+ adds @@dbt_model_name and other tags automatically, and you can add your own per project or per model (dbt).

Tableau: set tags through Initial SQL. Test it on one workbook first:

SET QUERY_TAGS['tool'] = 'tableau', QUERY_TAGS['workbook'] = [WorkbookName], QUERY_TAGS['user'] = [TableauServerUser];

The Tableau parameters you can use are listed in Initial SQL parameters.

CI builds: set query_tags on the CI target in profiles.yml, for example:

query_tags: '{"env": "ci", "pr": "{{ env_var(''PR_NUMBER'', ''none'') }}"}'

For CI scripts that use the Python connector, pass query_tags when you open the connection.

2. Serverless Jobs DBUs from the dbt tasks

What you described (9 Nov): on the daily dbt cost, serverless jobs DBUs are about as large as the SQL warehouse DBUs, and the dbt CLI accounts for roughly 40% of your serverless jobs DBUs, even though almost all of the real work runs on the warehouse.

Why it happens: a dbt task uses two kinds of compute. The SQL warehouse runs the SQL that dbt generates; a separate "dbt CLI compute" runs dbt Core itself.

"In SQL warehouse, select a SQL warehouse to run the SQL generated by dbt." [...] "Choose dbt CLI compute to run dbt Core. Databricks recommends using serverless compute for jobs or classic jobs compute configured with a single-node cluster." (dbt task for jobs)

The CLI does little computing itself, but it stays up for the whole dbt command: it parses the project, sends queries, and then waits while the warehouse runs them. So a long or queued dbt run also costs more on the CLI side. Confirm this with your own data: compare the CLI task's serverless DBUs per run with the run's duration in system.lakeflow.job_task_run_timeline.

Recommendations, in order:

  1. Shorten the dbt runs. Every minute a dbt run spends queued on the warehouse is also paid for on the CLI. Raising max clusters on the dbt warehouse (see 1b) lowers both.
  2. Start the CLI fewer times. With 58 dbt jobs, and orchestrator chains where each product job is its own dbt task, every task starts its own CLI and re-parses the 313-model project. Group the models of a chain into one dbt build with selectors, raise threads so the warehouse is kept busy, and avoid separate tasks for deps, seed and run where one command will do.

  3. Use standard performance mode for dbt jobs that aren't time-critical. Keep performance optimized for the hourly UA chain that feeds the P0 automation.

    "Both modes use the same SKU, but standard performance mode consumes fewer DBUs, reflecting lower compute usage." (Run jobs on serverless)

  4. Test a classic single-node cluster for the CLI on one long-running chain. It's the other documented option (dbt CLI compute), and you already have pools to soften the start-up. See single-node compute for the setup. The trade-off is start-up time and paying the Azure VM cost again. Compare a week of each on the same chain before switching more.

3. Single workspace for dev and prod

Recommendation: split into a dev workspace and a prod workspace on the same metastore. Bind each environment catalog to its workspace and set the default catalog per workspace. Your bundle targets and Terraform map onto this directly.

"Use your single-region metastore for all software development lifecycle scopes and business units, for example, dev, test, prod, sales, and marketing." (UC best practices)

"Access from an unbound workspace is denied, even for users with explicit privilege grants on the catalog." (Workspace-catalog binding)

"When binding a catalog to a workspace, you can optionally restrict that workspace to read-only access." (same page)

  • analytics_prod can be bound read-only into dev for testing against real data, so an unqualified write can no longer land in prod.
  • Setting the default catalog per workspace (Default catalog) removes the unqualified-name risk.

4a. Zerobus Ingest: push ingestion without Kafka

"Zerobus Ingest is a push-based streaming API that writes data straight into Unity Catalog Delta tables at high scale, with no message bus to run." (Zerobus Ingest overview)

Zerobus Ingest is serverless and available in West Europe (region table). There's nothing to deploy: your producers call one endpoint per workspace, and the records land in a Unity Catalog table.

Where it fits for you

Today With Zerobus What goes away
Payment webhooks → n8n → SQL warehouse single-row INSERTs n8n posts each event to the REST API Warehouses kept awake 24/7; thousands of tiny Delta commits
Airflow producer → Kafka topic → Databricks sink job (Pattern A) Airflow tasks write directly with the Python SDK, or keep the producer code and point it at the Kafka-compatible API The Kafka hop and the sink jobs on pool clusters
Debezium CDC → Kafka Possible, but you'd still need the LSN-ordered MERGE downstream; the PostgreSQL connector is the better fit for CDC
Prometheus/Grafana on AKS (optional) The OpenTelemetry interface lands traces, logs and metrics in Delta Part of the self-hosted observability stack

How it works

  • No topic setup. The target table is the topic. You create the table, then push to it. For the Kafka-compatible API:

    "A Kafka topic name is the full three-level Unity Catalog table name (catalog.schema.table). The target table must already exist, because Zerobus never creates topics." (Kafka-compatible APIs)

  • Target table. It can be a regular managed Delta table or a streaming table:

    "Zerobus Ingest can write to both managed Delta tables and streaming tables, which work the same way, with the same limits and quotas." (Use Zerobus Ingest)

    Downstream it's a normal table: dbt incremental models, readStream, Genie and Tableau all work on it. - Latency. Records are durable in about 150 ms and in the table in about 5 seconds (Quotas). - Delivery: at least once, so deduplicate downstream (for example, MERGE on the payment event ID in silver):

    "Zerobus Ingest provides at-least-once delivery when the protocol provides a durability acknowledgment and the client retries records that aren't acknowledged." (Quotas)

Interfaces for your producers

Producer Interface Notes
n8n (webhooks) REST API JSON body, OAuth token refreshed hourly
Airflow tasks Python SDK (gRPC) Highest throughput, per-record acknowledgments
Existing Kafka producers Kafka-compatible API JSON only, no compression, write-only, public endpoint only

Schema contract

"Your table schema is the contract for what Zerobus Ingest accepts, and Zerobus Ingest never auto-evolves it." (Use Zerobus Ingest)

  • To change the schema, evolve the table first, then the producer.

  • Payment providers add webhook fields over time, so add a rescue column. It's a nullable VARIANT column tagged zerobus-rescue (JSON ingestion only).

    "Fields that don't fit the schema are grouped into a JSON object and stored in a designated rescue column as a VARIANT type." (Rescue column)

Security and networking

  • Authentication: a service principal with USE CATALOG, USE SCHEMA and MODIFY, SELECT on the target table gets a table-scoped OAuth token. Microsoft Entra ID federation is also supported.

  • Private Link and storage firewall:

    "MQTT and Kafka-compatible APIs don't support front-end Private Link and must use the public endpoint." (Networking)

    If the ADLS account behind your UC storage root has a firewall, allowlist the Databricks serverless outbound IPs (same page).

Limits (all adjustable, far above your volumes): 100 MB/s and 100,000 records/s per gRPC stream, 10,000 REST requests/s, 10 MB per record, unlimited concurrent streams (Quotas).

Cost

  • Rate: $0.072/GB ingested in West Europe (0.143 DBU per GB), with compute included and no idle cost (pricing).
  • On the bill: it appears as Automated Serverless. Track it with billing_origin_product = 'LAKEFLOW_CONNECT' in system.billing.usage (overview).
  • Example: 100k payment events a day at about 2 KB each costs under $1 a month.

Things to watch

  • Unflushed data: if Zerobus can't write to the table (for example, it was dropped or broken), it buffers the data, but not forever:

    "If the data remains unflushed for 28 days, the service deletes the buffered data and emits a per-stream discard event recording the number of records and bytes dropped." (Quotas)

    Route those events into your Alert Hub. - Table layout:

    "Databricks recommends using liquid clustered tables with Zerobus Ingest instead of partitioning." (Quotas)

    Keep predictive optimization on for the target tables.

Suggested pilot: 1. Payment webhooks first: one n8n flow → REST → a bronze.payment_webhooks table with a rescue column. Run it side by side with the current INSERT path for a week, and compare row counts and warehouse uptime. 2. Then move one Pattern A DAG from Kafka to the Python SDK, and measure the sink-job cost removed.

5. Semantic layer: multi-fact metric views, Tableau and Genie

Recommendation: the bridge pattern you built is the documented approach. Speed it up with materialization only where the source tables carry no RLS or ABAC.

"To combine measures from two or more fact tables that sit at different grains, define a bridge that enumerates the valid combinations of the dimensions the facts share, directly in the metric view's source." (Metric view joins)

"You can't materialize a metric view when the view or any of its source tables uses row-level security (RLS), column masks, or attribute-based access control (ABAC) policies." (Materialization)

  • This matters with your BU/app row filters: keep the pre-aggregated bridge as a regular, ABAC-governed table, and use materialization on unrestricted metric views.

  • Tableau: use Custom SQL with MEASURE(), BI compatibility mode, or a wrapper view.

    "Use Tableau's Custom SQL connection option with the MEASURE() pattern, or enable BI compatibility mode from the Initial SQL field in the connection dialog." (BI tools)

  • Genie: add metric views directly as Genie data sources, so Genie and Tableau share one definition (Query metric views).

6. ABAC: nested-policy errors and PII masking

Likely cause of the error: the BU policy and the app policy both match the same table for the same user. That produces two different row filters, and ABAC blocks it.

"Only one distinct row filter can be applied at query time for a given table and user. [...] If multiple distinct filters or masks apply to the same user and table (or column), Azure Databricks blocks access and returns an error." (Policy evaluation)

  • Fix: use one row-filter policy whose UDF takes both the BU and the app columns. Also remove any manually applied table filters, which conflict with ABAC too. Use SHOW EFFECTIVE POLICIES to diagnose.

  • PII: turn on data classification (Public Preview). It auto-tags IP addresses, names and similar columns, and one ABAC column-mask policy on those tags then covers current and future tables.

    "Databricks recommends using Attribute-based access control in Unity Catalog to create governance controls based on data classification results." (Data classification)

  • Exempt the dbt and pipeline service principals in EXCEPT. Otherwise their outputs are built on filtered data:

    "If that identity is subject to an ABAC policy, the materialized view or streaming table permanently contains masked or filtered data." (ABAC requirements)

7. ML: from notebooks to a production path (pLTV)

Recommendation: train on UC feature tables, register models in UC with an alias, batch-score into gold, monitor, and deploy all of it as code with MLOps Stacks (which fits your bundle and GitHub Actions setup). Add real-time serving only if the product needs it.

"Databricks recommends that you deploy ML pipelines as code. This eliminates the need to promote models across environments, as all production models can be produced through automated training workflows in a production environment." (Model lifecycle in UC)

"Batch inference workloads can reference a model version by alias." (same page)

"The environment created by MLOps Stacks implements the MLOps workflow recommended by Databricks." (MLOps Stacks)

  • Features: Feature Store in UC.
  • Monitoring: data profiling on the scored table to track drift and accuracy.

8. Custom observability: what native monitoring can replace

Recommendation: keep the parts that are specific to your platform: contracts, dbt tests, Tableau extract status and the status page. Replace the collection and freshness plumbing with native features.

Your framework collects Native replacement
Job runs, durations, failures system.lakeflow.* tables (Jobs system tables)
Table freshness / completeness Anomaly detection across a schema (Data quality monitoring)
Real-time failure / duration alerts Job notifications to a webhook, which can be your n8n Alert Hub (Notifications)
Cost and business-metric checks SQL alerts on system tables and metric views

"Anomaly detection enables you to monitor data quality across all tables in a schema." (Anomaly detection)

"System tables do not support real-time monitoring." (System tables)

For P0 flows such as the bot feeds, keep alerting on job notifications, not on system tables. Job system tables typically land within an hour.
